# How Caching Works With the Explicit `f_jxl` / `f_avif` / `f_webp` URLs

This repo builds Cloudinary URLs with the format baked into the URL path
(`f_jxl`, `f_avif`, `f_webp`) instead of `f_auto`. This document explains why
that choice makes caching simple and deterministic, and shows the measured
proof that the cache is being honored.

All evidence below was captured live on 2026-09-20 against the real asset
`images/blog/Gulfstream-G800` on the `paulapplegate-com` cloud.

## The URL is the cache key

A typical URL generated by `src/lib/cloudinary-core.mjs` looks like:

```
https://res.cloudinary.com/paulapplegate-com/image/upload/f_jxl,q_auto,w_800/v1789258841/images/blog/Gulfstream-G800
```

Every part of the cache-relevant identity is in the path:

| URL component | Meaning | Cache role |
|---|---|---|
| `f_jxl` / `f_avif` / `f_webp` | Explicit output format | Different format → different URL → separate cache entry. No content negotiation needed. |
| `q_auto` | Automatic compression quality | Part of the transformation, so part of the cache key. |
| `w_800` | Width from the `<picture>` srcset | Each breakpoint width is its own cache entry. |
| `v1789258841` | Asset version (from `src/data/cloudinary-images.json`) | Natural cache-buster: re-upload the image and the version changes, so no stale content is ever served. |

Because the format is in the URL, three different URLs are cached as three
independent objects on the CDN. Nothing is shared or negotiated between them.

## Measured proof the cache is honored

Cloudinary delivers through Fastly and reports cache status in the
`Server-Timing` header. Look for `desc=hit` vs `desc=miss`.

### Repeated request for the JXL URL

```console
$ curl -sI "https://res.cloudinary.com/paulapplegate-com/image/upload/f_jxl,q_auto,w_800/v1789258841/images/blog/Gulfstream-G800"
```

```
content-type: image/jxl
etag: "b7a340ebdffc4f7fe3158a2d0b1ee6a0"
cache-control: private, no-transform, immutable, max-age=2592000
vary: Save-Data
server-timing: cld-fastly;dur=7;...;desc=hit,...
```

Second identical request, seconds later:

```
server-timing: cld-fastly;dur=4;...;desc=hit,...
```

Same `etag`, same `content-length`, and `desc=hit` with a 4–7 ms CDN time —
the object was served straight from the Fastly cache, not regenerated.

### All three explicit formats — each cached independently

| Format | ETag | Bytes | CDN status |
|---|---|---|---|
| `f_jxl` | `b7a340ebdffc4f7fe3158a2d0b1ee6a0` | 62,793 | `desc=hit` |
| `f_avif` | `b2b3f4f977a7d100fe51a1fcc467fd03` | 43,074 | `desc=hit` |
| `f_webp` | `dff030bee1609502743ff4b7b2e3ab53` | 55,924 | `desc=hit` |

Three distinct ETags and three cache hits: one cache entry per format, exactly
as the URL design intends.

### Contrast: a brand-new `f_auto` URL

The same image requested with `f_auto` (a URL nobody had fetched before):

```
server-timing: cld-fastly;dur=360;...;desc=miss,...,cloudinary;dur=331;...
```

`desc=miss`, 360 ms, and an extra `cloudinary;dur=331` segment — the request
had to go back to Cloudinary's servers to **generate** the derivative, then it
was stored in the cache. Every distinct URL pays this cost exactly once; after
that, it is a hit, as the JXL/AVIF/WebP rows above show.

## What each cache header means

```
cache-control: private, no-transform, immutable, max-age=2592000
```

- **`max-age=2592000`** — browsers cache the image locally for 30 days with no
  network traffic at all.
- **`immutable`** — the browser will not even send a conditional
  (revalidation) request during those 30 days. This is safe because the
  `v<version>` segment changes whenever the underlying asset changes.
- **`private`** — the object is cached by the browser and by Cloudinary's CDN,
  but generic shared proxies in between won't store it.
- **`no-transform`** — intermediary proxies are forbidden from re-encoding or
  recompressing the bytes, so the JXL/AVIF/WebP you asked for is the byte
  stream the browser receives.

```
vary: Save-Data
```

The **only** request-header variation the cache honors is `Save-Data`. There
is **no** `Vary: Accept` on these responses: the format does not depend on the
browser's `Accept` header, so one URL always serves one format and every
visitor hits the same cache entry. This is the core difference from `f_auto`,
where a single URL must yield different formats for different browsers and the
CDN has to fan its cache out by the requester's capabilities.

```
etag: "..."
```

A validator scoped to the exact format + width + version. If a revalidation
ever does happen (after `max-age` expires), the CDN/browser can answer `304
Not Modified` instead of resending the image.

## Why the hit ratio stays high

Two design choices in this repo keep the cache small and hot:

1. **Discrete widths only.** The srcset uses the breakpoint widths stored in
   `src/data/cloudinary-images.json` (plus `DEFAULT_WIDTHS`), e.g.
   `[50, 398, 588, 788, 980, 1118, 1289, 1429, 1630, 1672]` for JXL.
   Browsers choose the nearest listed width, so the CDN only ever sees a
   handful of distinct `w_` values per image instead of a continuum of
   arbitrary sizes — a small set of cache entries serves all visitors.
2. **Fixed format list.** `FORMATS = ['jxl', 'avif', 'webp']` in
   `src/lib/cloudinary-core.mjs` means exactly three format variants per width.
   Safari picks the JXL `<source>`, Chromium picks AVIF, the WebP `<img>`
   fallback covers everything else — but each of those choices maps to a
   stable, shared URL.

## How to verify it yourself

From the terminal, watch the `Server-Timing` status:

```console
# Run twice — the second run should say desc=hit
$ curl -sI "<any image URL from the site>" | grep -i server-timing
```

Or in the browser:

1. Open DevTools → **Network**.
2. Load a page, then reload it.
3. Image rows show **(disk cache)** or **(memory cache)** in the Size column
   on reload — that is `cache-control: immutable, max-age=2592000` doing its
   job.
4. Click a row and check **Response Headers** for `server-timing: cld-fastly;...;desc=hit`.

## Summary

- Explicit `f_jxl`/`f_avif`/`f_webp` put the format in the URL, so each
  variant is a separate, deterministic cache entry with no `Vary: Accept`
  fan-out.
- Measured: repeated requests return `desc=hit` from Fastly in single-digit
  milliseconds; the first request of a new URL returns `desc=miss` and
  generates the derivative once.
- `cache-control: private, no-transform, immutable, max-age=2592000` gives
  30-day browser caching with zero revalidation, and `v<version>` busts the
  cache automatically when an asset is re-uploaded.
- The manifest's discrete breakpoint widths keep the number of cache entries
  small, so the cache stays warm and hit rates stay high.
